# Quiby: автоматическое подключение и проба direct через NAT

## Автоматический режим

Лаунчер получает отдельный билет `/api/direct/config` для текущего разрешённого
Discord-аккаунта. frp проверяет билет при входе и heartbeat; публиковать прокси
может только домашний provider. Разрешены только `minecraft-direct` (XTCP) и
`minecraft-relay` (STCP), оба ведут на домашний `127.0.0.1:25565`.
Старые visitor-соединения без Login запрещены: `allowUsers` содержит только
роль `quiby-player`, без `*` и пустого имени.

При запуске игры лаунчер скрыто запускает проверенный frpc 0.71.1, прогревает
туннель и сравнивает пять настоящих Minecraft ping/pong по каждому маршруту.
Туннель выбирается при выигрыше медианы больше 5 мс без увеличения разброса.
Если прямой маршрут, авторизация или координатор недоступны, остаётся обычный
адрес сервера. STCP служит запасным вариантом внутри туннеля. TCP multiplexing
выключен, чтобы потеря пакета одного игрока не задерживала потоки остальных.
Маршрут выбирается перед подключением: текущую TCP-сессию нельзя перенести
между маршрутами без переподключения. Голосовой UDP остаётся без изменений.

Локальный порт выбирается автоматически, доступен только на `127.0.0.1` и
действует до закрытия игры. Билет, конфигурация и процесс очищаются при выходе.
Версия, контрольные суммы архива и frpc закреплены в исходниках; исполняемый
файл загружается только из официального GitHub Releases frp. Сертификат
координатора проверяется по CA из API, без отключения TLS-проверки.

Подготовка отдельного приватного установочного каталога:

```powershell
python deploy/direct/prepare_permanent.py --output temp/direct-permanent --api https://api.quiby.me
```

Порядок включения при выпуске обновления:

1. Развернуть новый API. Из приватного `api.env.json` передать в окружение API
   `DIRECT_SERVER`, `DIRECT_PORT`, `DIRECT_CA`, `DIRECT_PROVIDER_KEY`.
   До настройки этих значений API отвечает `enabled: false`.
2. Проверить, что 443/TCP на VPS свободен. Остановить только прежний тестовый
   unit Quiby, если он ещё занимает этот порт. Загрузить каталог `vps` на VPS и
   выполнить `sh install.sh` от root. Затем так же установить `home` на домашнем
   хосте Minecraft. Скрипты создают отдельные службы systemd с автозапуском,
   повторным запуском после ошибок и лимитом памяти 128 МиБ на службу.
3. Проверить TLS, отказ анонимному клиенту, доступ разрешённого аккаунта и
   выбор маршрута с внешнего компьютера. Затем выпускать лаунчер с новым модом.
   Старый HAProxy/WireGuard и публичный игровой адрес сохраняются.

Ключ provider и закрытый ключ TLS нельзя включать в установщик, модпак, Git
или ZIP для игроков. Сертификат действителен два года; перед истечением
обновить сертификат координатора, копию дома и `DIRECT_CA` в API вместе.
Откат: выключить обе службы `quiby-direct-coordinator` / `quiby-direct-provider`
и очистить `DIRECT_SERVER` в API. Обычный маршрут продолжит работать.

Проверки:

```powershell
npx tsx --test apps/server/src/__tests__/direct.test.ts apps/launcher/src/main/engine/__tests__/directRoute.test.ts
$env:QUIBY_FRP_TEST_DIR='temp/direct-test' # каталог официальных frpc.exe / frps.exe
npx tsx --test apps/server/src/__tests__/direct.test.ts
```

Вторая проверка поднимает изолированные реальные frp-процессы с временным
TLS-сертификатом, проверяет передачу данных, отказ legacy visitor без Login,
отказ анонимному frpc, автоматический запуск лаунчером и очистку его файлов.
В production она ничего не отправляет и ничего не разворачивает.

## Ручная двухчасовая проба

Пробный транспорт для Minecraft TCP, без обновления сборки или игрового мода.
На VPS работает координатор frp **0.71.1**, дома — provider, у проверяющего —
visitor. При успешном XTCP игровой трафик проходит прямо между домом и игроком.
При неудаче visitor использует STCP через VPS. Голосовой UDP эта проба не меняет.

Официальные бинарники закреплены SHA-256 из GitHub Releases. Используются TLS
с проверкой сертификата своего координатора и отдельные случайные тестовые ключи.
На компьютере игрока открыт только `127.0.0.1:25575`. На VPS нет веб-панели,
SSH-доступа через frp или публичных портов обратного TCP-прокси. Minecraft
по-прежнему проверяет вход существующим Quiby admission.

## Создание нового теста

Python 3.11+ и OpenSSL. Команда создаёт **новый** каталог и не изменяет работающие
службы, firewall, DNS, лаунчер или манифест:

```powershell
python deploy/direct/test_direct.py
python deploy/direct/prepare.py --server 185.146.157.76 --output temp/direct-trial-new
```

Получатся приватные папки `vps`, `home`, `player` и `quiby-direct-player.zip`.
Весь каталог содержит секреты и дополнительно исключён из Git собственным
`.gitignore`. Папка/ZIP `player` содержит только клиент, публичный сертификат и
временные ключи теста; закрытый ключ TLS остаётся только в папке VPS.

На VPS оператор загружает **папку vps**, проверяет, что TCP 443 свободен и
разрешён уже существующими правилами, затем запускает `sh start.sh` от root.
Если 443 занят, выберите другой разрешённый порт параметром `--port` и проверьте
правила отдельно. Скрипт не останавливает чужие службы и не правит firewall.
Координатор запускается отдельным transient systemd unit `quiby-direct443-test`
с `DynamicUser`, ограничением памяти 128 МиБ и временем работы **два часа**.
Право привязки к низким портам — единственная добавленная capability.

Дома оператор запускает `sh start.sh` из **папки home** на хосте Minecraft.
Клиент завершается через два часа. По умолчанию цель — `127.0.0.1:25565` этого
хоста. Запускайте его на хосте, а не в другом контейнере с отдельным localhost.
Minecraft должен быть уже запущен обычным способом через Crafty.

Проверяющий распаковывает **только player ZIP**, запускает `start.cmd`, оставляет
окно открытым, запускает Minecraft обычным лаунчером Quiby и подключается к
`127.0.0.1:25575`. Автоматический вход на старый адрес при необходимости отменяется.
В логе успешный direct обозначен `establishing nat hole connection successful`;
`remoteAddr` показывает выбранный адрес. После неудачного direct первый вход
может ждать до четырёх секунд перед резервным соединением. Уже установленная
игровая сессия не переносится между маршрутами без переподключения.

Ключи **только для доверенных проверяющих**, не для публичного распространения.
Это не готовая модель выдачи доступа 25 игрокам: перед интеграцией в лаунчер
нужны персональная авторизация, жизненный цикл процесса и проверка внешних сетей.
Общий тестовый ключ не следует включать в публичный лаунчер или манифест.

## Измерения

```powershell
python deploy/direct/probe.py 127.0.0.1 25575
python deploy/direct/probe.py play.quiby.me 25565
```

Скрипт проверяет ответ status и точный Minecraft pong, отдельно измеряя время
пакета ping/pong. Поддерживает фрагментированные ответы, ограничивает размер
пакета и проверяет nonce. Первый запуск frp может включать установление туннеля;
повторите замер после успешного соединения. Для временного диагностического
echo-сервиса есть `--echo`; его нельзя применять к игровому порту.

В пробе 22.10.2026: frpc определил домашнюю сеть как `EasyNAT / BehaviorNoChange`.
Настоящие provider в CasaOS и visitor в Windows установили QUIC XTCP напрямую
между `192.168.18.100` и `192.168.18.18`. Диагностический обмен дал медиану около
**2 мс напрямую и 113 мс через Москву**. Это **проверка внутри одной домашней сети**,
а не обещание пинга внешним игрокам. Во время этого замера Minecraft в Crafty
был остановлен; использовался отдельный echo-сервис на loopback.

После запуска Minecraft диагностический сервис остановлен, provider переключён
на настоящий игровой порт. Шесть Minecraft ping/pong дали медианы **1,15 мс**
через прямой LAN-туннель, **95,35 мс** через обычный `play.quiby.me:25565` и
**89,42 мс** через принудительный STCP. Это всё ещё замер с домашнего ПК.

Дополнительный visitor на VPS проверен с запрещёнными для его процесса
RFC1918/CGNAT-адресами: публичный NAT-туннель не установился (таймаут), а
Minecraft ping/pong через резервный STCP дал медиану **60,67 мс**. Повтор без
этого ограничения выбрал `10.77.0.2` — существующий WireGuard, поэтому его
нельзя считать обходом Москвы или доказательством публичного direct.
Оба диагностических visitor на VPS остановлены. Польза для внешних игроков
пока **не подтверждена**; нужен тест из их сети, а не сравнение разных точек
измерения между собой. Для уже запущенного координатора дополнительно поставлен
явный systemd timer, останавливающий службу в исходный двухчасовой срок.

Cloudflare STUN отвечал на обычный Binding Request, но не предоставлял вторую
адресную точку, нужную этой версии frp для определения NAT. Для пробы использован
штатный `stun.easyvoip.com:3478`; это устранило `not enough addresses`.

## Остановка и ограничения

VPS: `systemctl stop quiby-direct443-test`. Дома — остановить **свой** `frpc`;
если он запущен указанным скриптом, он сам завершится через два часа. У игрока —
закрыть окно `start.cmd`. Существующий `play.quiby.me:25565`, HAProxy и WireGuard
при установке/остановке пробы не изменяются. В текущем тесте использован ранее
разрешённый и свободный 443; правило для нового порта firewall не добавлялось.

Документация транспорта: [XTCP](https://gofrp.org/en/docs/features/xtcp/),
[релиз 0.71.1](https://github.com/fatedier/frp/releases/tag/v0.71.1).
