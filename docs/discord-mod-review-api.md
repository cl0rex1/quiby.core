# API заявок для Discord-бота

Бот работает с REST API quiby, без доступа к SQLite и без административного ключа лаунчера. Код Discord-бота в этом репозитории отсутствует; здесь реализована серверная часть интеграции. Сообщения в Discord автоматически не отправляются.

## Настройка

На backend и в окружении бота задать одинаковый **MOD_REVIEW_BOT_API_KEY**, случайный секрет минимум 32 символа. Генерация: `openssl rand -hex 32`. Передавать ключ заголовком `X-Bot-Key`, по HTTPS при удалённом соединении. В лаунчере и переменных `VITE_*` ключа быть не должно.

Пустой ключ отключает API (503). Неверный — 403. Ключ даёт доступ только к чтению и рассмотрению заявок на моды, не к пользователям, новостям или публикации сборок.

## Поток

1. Игрок отправляет заявку из лаунчера. Сервер получает Discord ID и Minecraft-ник из проверенной JWT-сессии, а не из присланных полей.
2. Бот получает новые заявки и создаёт сообщение с кнопками «Одобрить» / «Отклонить» в модераторском канале.
3. При нажатии бот проверяет сервер Discord и роль модератора, затем отправляет решение в API.
4. Сервер сохраняет автора решения, причину и время; результат проверки SHA-1 меняется атомарно с заявкой.
5. Игрок повторяет проверку мода в лаунчере. Перед запуском файл также проверяется в основном процессе Electron.

Заявка содержит метаданные и SHA-1, не сам JAR. Одобрять следует после проверки именно соответствующей версии файла. Имена известных запрещённых модов продолжают блокироваться даже при ручном одобрении хеша.

## Методы

### Заявка игрока

`POST /api/mods/whitelist-request` с `Authorization: Bearer <session.token>`.

```json
{
  "mod_name": "Example Utility",
  "filename": "example-utility.jar",
  "hash_sha1": "0123456789abcdef0123456789abcdef01234567",
  "reason": "Описание назначения мода, минимум 10 символов.",
  "project_url": "https://example.com/mod"
}
```

Ответ: `{ "success": true, "request": { "id": 42, "status": "pending" }, "message": "..." }`.
Повторная заявка того же игрока на тот же хеш, пока она pending, возвращает прежний ID. Ссылка необязательна, разрешены HTTP/HTTPS.

### Очередь бота

`GET /api/bot/mod-whitelist-requests?status=pending&after_id=0&limit=50`

Все методы ниже требуют `X-Bot-Key`. Параметры: status = pending / approved / rejected, after_id ≥ 0, limit = 1–100.

Ответ содержит `requests`, `has_more`, `next_after_id`. Записи упорядочены по ID, включают поля заявки, project_url, reviewer_discord_id, decision_reason, reviewed_at.

Бот хранит соответствие request ID → Discord message ID. Курсор сохраняется **после успешной отправки сообщения**. Если has_more=true, загрузить следующую страницу. Иначе продолжать опрос с паузой (например, 15–30 секунд). При неудаче повторить с прежним курсором. Не дублировать сообщение для уже известного ID.

### Одна заявка

`GET /api/bot/mod-whitelist-requests/42` → `{ "request": { ... } }`, либо 404.

### Решение

`PATCH /api/bot/mod-whitelist-requests/42`

```json
{
  "decision": "approved",
  "reviewer_discord_id": "123456789012345678",
  "reason": "Версия файла проверена, запрещённых функций не обнаружено."
}
```

- decision: approved / rejected.
- reviewer_discord_id: ID модератора, 17–20 цифр.
- reason: 3–1000 символов.
- 200: решение сохранено; вернуть/обновить сообщение по полю request.
- Повтор с тем же решением возвращает 200 и первоначальные данные аудита.
- 409: уже принято другое решение; повторно получить заявку и обновить кнопки.
- 400: неверный ID или тело; 404: заявки нет.
- На 5xx повторять запрос с тем же ID и решением.

Решение относится к хешу файла глобально. Отклонённый хеш не разрешается через каталог модов; новое одобрение версии обновляет результат. Для повторного пересмотра нужна новая заявка, существующее решение не переписывается.

Старый `GET /api/mods/whitelist-requests` теперь требует административную авторизацию. Боту следует использовать ограниченный `/api/bot/...`.
